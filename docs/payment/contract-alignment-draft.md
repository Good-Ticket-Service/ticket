# 결제 계약 정합화 초안

- 상태: 초안. 기존 `docs/shared/` 계약을 대체하지 않는다.
- 근거: 2026-10-26 HANDOFF의 팀 결정, 이슈 #7.
- 제공: 결제(강현민). 소비: 예매(지한얼).
- 반영 순서: 계약 이슈의 합의 확인 → 문서만 담은 계약 PR → 구현.

## 계약 변경안

| 항목 | 현재 계약 | 변경안 |
|---|---|---|
| 준비 요청 `userId`, `sellerId` | UUID | Long. DB는 BIGINT다 |
| 준비 요청 쿠폰 | `couponId` | `userCouponId`. 쿠폰 소유 모듈의 사용권 ID다 |
| 결과 불명 | IN_PROGRESS를 유지하고 차단·관리자 확정 | PG 승인 요청 후 1분 안에 결과를 모르면 FAILED로 확정해 좌석을 풀고, 나중에 승인이 발견되면 대사가 자동 환불한다 |
| 결과 불명 실패 사유 | 없음 | `failureCode=PG_UNRESOLVED`, `failureType=UNAVAILABLE` |
| 관리자 결제 확정 | `resolve`, 결제 `unblock`, `MANUAL` | 제거한다. 환불 재시도와 환불 차단 정책은 별도로 구분한다 |
| FAILED 설명 | 돈이 오가지 않음으로 확정 | 해당 결제 시도를 종료한다. 결과 불명으로 종료한 건은 늦은 승인에 대한 자동 환불 책임이 남는다 |
| 공연 취소 | `SCHEDULE_CANCELED` 사유가 이미 있다 | 예매가 예약별로 환불 API를 호출한다. 취소 기한·수수료와 무관하게 전액 환불한다 |
| 예매 취소 의도 | CANCEL_PENDING이 제안으로 남아 있다 | 외부 환불 호출 전에 CANCEL_PENDING을 커밋하고, 복구 잡이 재시도한다. 예매 소유 상태다 |
| 결제 결과 전달 | HTTP 조회와 향후 이벤트가 혼재한다 | 예매가 결제 상태를 폴링한다. 결제는 결과를 푸시하지 않는다 |
| 대기열 | 결제 계약에 명시가 없다 | 토큰은 좌석 조회·선점 입장권이다. 결제·예매 API에서 검사하지 않는다 |

1분은 `approveRequestedAt`을 기준으로 센다. 첫 조회와 반복 조회 간격은 10초 이내로 설계하고, NotFound 유예는 1분이다. 조회 Unknown이 계속돼도 1분 뒤 PG_UNRESOLVED로 종료한다. 대사는 FAILED 확정 후 11분·1,440분 체크포인트를 사용한다. 11분은 결제 실패 확정 대기 시간이 아니다.

예매는 FAILED를 관측하면 기존 결제 시도를 종료하고 좌석 선점을 해제한다. 이후 발견한 승인은 예매를 다시 확정하지 않고 결제가 자동 환불한다. 실패 확정과 동시에 쿠폰을 반납하고, 늦은 승인 자동 환불에서는 쿠폰을 다시 변경하지 않는다.

`docs/shared/internal-api/payment.md`의 준비 요청·failureType·관리자 API·결과 조회 설명·합의할 항목을 위 내용으로 정리하고 변경 이력을 추가한다. `docs/shared/conventions.md`의 회원 ID 협의 필요 문구도 Long으로 정리한다. 시각 오프셋과 X-Username 제거는 별도 근거 없이 공통 계약을 변경하지 않는다.

## 현재 구현에서 확인한 범위

- `Payment`, `PaymentOrder`, 테스트 fixture의 회원·판매자 ID가 UUID다. `schema.sql`도 UUID다.
- Payment에 차단·차단 해제·give-up 판정이 있고 `PaymentFailureCode.MANUAL`이 있다.
- Refund가 같은 Recovery 임베디드를 쓴다. 결제 차단을 없애면서 환불 재시도 정보를 함께 없애지 않는다.
- 결제 application 흐름, 복구 스케줄러, 내부 컨트롤러는 아직 없다. 관리자 resolve API도 구현 전이다.
- `backend/config-repo/payment-service.yml`에 recovery 설정이 없다. 문서의 설정값을 현재 실행 중인 설정으로 취급하지 않는다.
- `SCHEDULE_CANCELED` 요청 사유는 기존 내부 계약에 이미 있다. 전액 환불 보장 설명을 보강하면 된다.
- `CANCEL_PENDING`은 현재 결제·환불 enum에 추가할 상태가 아니라 예매의 내구성 있는 취소 의도다.
- 테이블의 `p_` 접두사는 팀 결정 전까지 유지한다.

## 구현 검증 기준

계약 반영 뒤 ID 타입과 DDL·테이블 문서를 함께 바꾼다. 결과 불명 실패는 1분 직전에는 확정하지 않고 정확히 1분부터 확정하는 경계 테스트를 둔다. 늦은 승인과 중복 대사가 겹쳐도 환불은 한 건만 만들어야 한다. FAILED 처리 후 쿠폰 반납과 AUTO_VOID의 쿠폰 미변경을 확인한다. 환불 호출 전 취소 의도가 저장되고 응답 유실 뒤 재시도되는지는 예매 담당과 통합 검증한다.

JAVA_HOME을 변경하지 않고 payment 테스트와 전체 Gradle build를 실행한다. Docker가 필요한 스키마 통합 테스트의 실행 여부를 별도로 기록한다. 구현이 없는 현재 단계에서 이 동작들이 검증됐다고 보고하지 않는다.
