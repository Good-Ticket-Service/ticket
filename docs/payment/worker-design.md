# 결제·환불 워커 실행 설계

- 상태: 설계안. 워커 분리·Inbox·Outbox 구현이나 성능 개선이 완료됐다는 뜻이 아니다.
- 담당: 강현민
- 기준: [plan.md](plan.md)의 트랜잭션·복구 규칙, [decisions.md](decisions.md) D14·D15·D16
- 적용 시점: 고도화(Phase 3, 트러블슈팅 기간). 1차 MVP 범위가 아니다. 동기 MVP·복구를 먼저 구현하고 대량 환불·Kafka 실험에서 단계적으로 적용한다.

## 1. 목적과 용어

결제 요청 접수와 실제 PG 호출을 구분한다. PG 지연·대량 환불이 조회 API 자원을 얼마나 점유하는지 측정하고, 접수한 일을 프로세스 종료 뒤에도 이어갈 수 있게 한다. 준비 → 사용자 인증 → 승인 → 예매 확정의 업무 순서는 그대로다.

| 용어 | 책임 | 완료를 뜻하는 범위 |
|---|---|---|
| API 역할 | 준비·승인·환불 접수, 조회, 관리자 요청 검증 | 계약에 정한 접수 또는 업무 결과 |
| 워커 | 실행 대상 점유, PG 호출, 결과 저장, 복구·대사 | 개별 실행 시도의 처리 |
| 영속 작업 | 다음에 해야 할 일을 DB에 남긴 기록 | 실행 예정이 저장됨. PG 성공과 다르다 |
| Outbox | 업무 상태와 함께 저장한 발행 대기 기록 | 발행 의도 저장. Kafka 전달 완료와 다르다 |
| Inbox | 받은 메시지를 업무 또는 영속 작업에 인계한 기록 | DB 인계 완료. PG 처리 완료와 다르다 |
| offset 커밋 | Kafka 소비 그룹의 처리 위치 기록 | DB·PG 성공을 대신하지 않는다 |

워커는 실행 역할이다. 같은 앱 안의 실행 풀·스케줄러·Kafka 소비자도 워커가 될 수 있다. 별도 업무 서비스나 Kafka를 도입해야만 워커를 쓸 수 있는 것은 아니다.

## 2. 실행 역할을 나누는 순서

| 단계 | 구성 | 확인할 것 |
|---|---|---|
| 1. 동기 기준선 | 한 프로세스에서 API·Inline 승인·복구 실행 | 정상 완료 지연과 장애 시 영향 |
| 2. 실행 풀 분리 | 같은 프로세스에서 접수·조회와 환불·복구의 실행 풀 및 동시성 분리 | PG 지연이 API 스레드를 점유하는지 |
| 3. 프로세스 분리 | 같은 payment-service 코드와 DB를 쓰는 API 역할·워커 역할 별도 실행 | 자원 격리 효과와 DB 병목 |
| 4. Kafka 인계 비교 | 소비자 직접 실행과 DB 인계 후 워커 실행 비교 | 재시작 복구·소비 지연·추가 DB 비용 |

첫 적용 대상은 환불·복구·대사다. 승인·준비는 기존 동기 경로를 유지한다 (D16). 프로세스를 나눠도 같은 DB·PG 한도를 공유하므로 부하가 완전히 격리됐다고 주장하지 않는다.

프로세스 분리 시 다음 책임을 설정으로 구분한다. 설정 이름과 Compose 구성은 구현 작업에서 정한다.

- API 역할: Controller와 요청 검증·조회, 동기 Inline 승인의 PG 호출을 담당한다.
- 워커 역할: 환불 실행·복구·대사 및 선택한 Kafka 수신·발행 작업. 외부 요청을 받는 Controller는 등록하지 않거나 접근을 차단한다.
- 역할별 스케줄러·소비자·발행기를 명시한다. 승인 결과 1분 확정에 필요한 복구 작업도 반드시 실행되게 한다.
- 환불을 워커 전담으로 바꾸면 API의 커밋 직후 직접 cancel 호출은 끈다. 같은 최초 실행을 양쪽에서 시작하지 않게 하고, 다른 실행 경로도 같은 점유 절차를 거친다.

역할 분리만으로 기존 응답·상태 의미를 바꾸지 않는다. 기존 계약과 달라지면 먼저 계약 이슈로 합의한다. 결과 이벤트를 도입해도 준비·승인은 동기 Feign, PG 호출은 HTTP로 유지한다. 승인 응답도 DONE·FAILED·IN_PROGRESS다.

## 3. 기존 상태를 영속 작업으로 활용한다

`Payment.IN_PROGRESS`, `Refund.REQUESTED`, `next_attempt_at`, `recovery_started_at`은 미완료 처리의 영속 기록이다. 구현할 복구 잡이 이 기록을 처리한다. 별도 `payment_job` 테이블을 기본 구성으로 추가하지 않는다.

| 기존 기록 | 워커가 할 일 |
|---|---|
| 만료된 Payment.READY | PG 호출 없이 만료 처리 |
| 조회 시각이 된 Payment.IN_PROGRESS | PG 상태 조회. 승인을 무조건 재전송하지 않는다 |
| 차단되지 않은 Refund.REQUESTED | 같은 취소 키로 PG 취소·결과 확인 |
| 대사 대상 FAILED 결제 | 늦은 승인 조회, 필요하면 ensureRefund |

별도 작업 테이블은 접수 의도·점유·취소·다단계 실행을 기존 기록으로 표현하기 어려울 때만 도입한다. 도메인 상태는 업무 결과, 작업 상태는 실행 여부를 나타낸다. 다음 실행을 결정하는 기록은 하나로 정하고 중복 스케줄링하지 않는다. 분리된 기록의 생성·완료 전이는 같은 DB 트랜잭션에 저장한다. 컬럼·인덱스는 구현 전에 tables.md와 DDL에 함께 정의한다.

## 4. Kafka 수신과 PG 실행의 인계

### 소비자가 직접 실행

```text
Kafka 수신 → DB 상태 확인·점유 → 트랜잭션 밖 PG 호출 → 결과 저장 → offset 커밋
```

단계가 적지만 느린 PG 호출이 소비 처리를 지연시킨다. DB 커밋 후 offset 커밋 전에 종료하면 재전달될 수 있다. 재실행은 업무 상태·멱등 키로 판단한다.

### DB 인계 후 별도 워커 실행

인계 대상은 환불 명령과 확정 실패 보상이다. 승인 명령은 이 경로로 보내지 않는다.

```text
Kafka 수신
  → 하나의 DB 트랜잭션
      processed_event에 eventId 기록 (Inbox 역할)
      환불 의도·REQUESTED 또는 WAITING 저장
    커밋
  → offset 커밋

워커
  → 실행 가능한 REQUESTED 점유·커밋
  → 트랜잭션 밖 PG 취소
  → 상태 재확인·환불 결과 저장
```

- 기존 `processed_event`가 Inbox 역할을 맡는다. 같은 목적의 inbox 테이블을 추가하지 않는다. 소비자 식별자와 eventId의 유니크 범위는 구현 시 정한다.
- Inbox만 먼저 저장하거나 offset을 업무 인계 전에 커밋하지 않는다. 재전달을 무시해도 되는 시점은 실행 책임이 DB에 남은 뒤다.
- 서로 다른 eventId가 같은 orderId의 환불을 요청할 수 있다. 메시지 중복 방지와 업무 멱등성은 별도이며 결제당 환불 1건 제약을 유지한다.
- WAITING·NOT_REQUIRED 등 기존 환불 계약을 적용한다. 모든 명령을 무조건 REQUESTED로 만들지 않는다.
- 승인 요청·pgAuthToken은 Kafka·Inbox·Outbox에 저장하지 않는다. 환불 명령·결과 이벤트에도 인증값을 넣지 않는다.

Outbox는 발신 측 업무 상태와 발행 의도를 같은 트랜잭션에 저장한다. 발행 ACK 유실은 재발행을 만들 수 있으므로 중복 수신을 전제로 한다. 접수 응답이 무엇의 영속 저장을 보장하는지 계약으로 정하고, ACK 타임아웃을 이미 저장된 결제·환불의 취소로 간주하지 않는다. 다른 서비스의 Outbox 도입을 이 문서로 일방 확정하지 않는다.

## 5. 점유·재시작·PG 호출 한도

- 짧은 트랜잭션에서 후보를 `FOR UPDATE SKIP LOCKED`로 점유하고 커밋한 뒤 PG를 호출한다. 네트워크 대기 동안 DB 잠금·트랜잭션을 유지하지 않는다.
- 점유 만료 후 다른 워커가 인수해도 이전 PG 호출은 살아 있을 수 있다. 소유자·버전 검사는 오래된 결과 저장을 제어하지만 외부 과금을 취소하지 않는다. PG 멱등성·조회·대사·ensureRefund를 함께 유지한다.
- 오래된 워커 결과도 무조건 버리지 않는다. 늦은 승인은 FAILED를 DONE으로 되살리지 않고 자동 환불 경로로 처리하며 중복 환불을 막는다.
- 프로세스 종료 후 실행 대상이 다시 조회돼야 한다. 처리 불명인 PG 호출은 조회·기존 복구 규칙으로 이어간다.
- PG별 승인·취소·조회의 실행 풀과 동시성 상한을 구분한다. 대량 환불 중에도 승인 결과 1분 확정을 위한 조회 자원을 확보한다.
- 호출 속도와 동시 실행 수는 별도로 제한한다. 여러 인스턴스의 합계가 PG 한도를 넘지 않게 공유 제한 또는 인스턴스별 예산을 설계한다.
- 재시도는 기존 백오프·차단 정책을 따른다. DLT 이동이나 시도 횟수 소진만으로 환불 책임을 종료하지 않는다. 미완료 거래·경보·관리자 재처리 경로를 남긴다.

## 6. 동기 승인과 환불 큐의 시간 기준

```text
예매 → Feign 승인 요청 → Inline 실행 직전 만료 확인 → HTTP PG 승인 → 결과 확인
                                                         결과 확정 시한 1분

환불 명령 → Kafka·DB 대기 → 환불 워커 점유 → HTTP PG 취소 → 환불 완료 확인
```

승인은 Kafka 큐에 넣지 않는다. HTTP 전달·실행 대기 뒤 PG 호출 직전에 만료·현재 상태를 다시 확인한다. 1분은 `approve_requested_at`부터 세며 요청 전체 지연과 구분한다. 승인 한도 초과 시 접수·거절 정책은 대기열·예매 담당과 합의한다.

환불은 이미 접수한 처리 책임이므로 좌석 선점 만료를 이유로 버리지 않는다. 큐 대기부터 완료까지 지연, 가장 오래된 미완료 환불과 차단 시한을 관측한다. 큐·실행 풀의 용량과 포화 정책을 명시하고 기존 환불을 조용히 드롭하지 않는다.

같은 결제의 파티션 키만으로 다른 orderId의 늦은 결과까지 막히지는 않는다. 결제는 orderId 멱등성을 유지하고 예매는 현재 시도의 결과인지 확인한다.
