# 결제·환불 실험 계획

동기 구현의 한계를 측정하고, 개선 전후를 같은 조건에서 비교한다. 구현 규칙은 [plan.md](plan.md), 작업 순서는 [todo.md](todo.md)에 있다.

## 측정 환경 두 가지

개선 효과는 **단독** 환경에서 비교하고, **전체** 환경은 마지막에 효과가 유지되는지 확인하는 데만 쓴다.

| | 단독 (주 실험) | 전체 연결 (보조 실험) |
|---|---|---|
| 경로 | k6 → payment 내부 API → fake-pg | k6 → Gateway → 예매 → payment → fake-pg |
| 띄우는 것 | payment, fake-pg, PostgreSQL, (Kafka), Prometheus·Grafana | 전체 Compose |
| k6 위치 | `ticket-net`에 붙은 컨테이너. 내부 API는 Gateway 라우트와 호스트 포트가 없으므로 `http://payment-service:8084`로 부른다 | 호스트 또는 컨테이너에서 Gateway로 |
| 쓰는 이유 | 바꾼 변수 하나의 효과만 보인다. 다른 팀원 일정·코드와 무관하게 언제든 같은 조건으로 다시 돌린다 | 다른 서비스로 번지는 영향은 전체 연결에서만 보인다 |
| 시점 | 내 구현(Task 12)이 끝나면 바로 | 예매 연동(Checkpoint B)이 안정된 뒤 트러블슈팅 기간 끝에 1~2회 |

단독 환경에서 k6는 예매 대신 `준비 → 결제창 대체 → 승인`을 직접 호출하고, `expiresAt`도 직접 넣는다.

## 측정 규칙

- 측정 환경(머신, 인스턴스 수, 설정값, 단독/전체)을 결과와 함께 기록한다.
- 한 번에 변수 하나만 바꾼다.
- 워밍업 후 3회 측정하고 중앙값을 쓴다.
- 도구는 k6 + Prometheus/Grafana이고, 결과는 `docs/payment/perf/`에 둔다.
- 아래 숫자는 실험 입력값이다. 결과 칸은 실측으로만 채운다.
- API 접수 응답과 실제 업무 완료를 구분한다. 승인 완료 TPS는 서로 다른 신규 결제가 PG 승인 결과를 확인해 DONE으로 DB에 저장된 건수이며, 조회·재시도·접수 응답은 더하지 않는다. FAILED 시도 종료와 늦은 승인 환불까지의 금액 정합성 해소는 별도로 센다.
- 워커 비교는 총 CPU·메모리·DB 연결 예산과 PG 제한을 맞춘다. Compose의 `cpus`·`mem_limit` 합계와 Hikari `maximum-pool-size` 합계를 단일 프로세스와 같게 고정한다. 프로세스를 늘려 자원도 함께 늘린 결과를 역할 분리만의 효과로 해석하지 않는다.
- 일정 유입률 시험에서는 목표·실제 유입률, k6 dropped_iterations와 부하 발생기 자원을 기록한다. 도구의 요청 생성 한계와 서비스의 처리 한계를 구분한다.

### 시나리오 4의 세부 장애 행렬

아래는 실행할 실험 계획이다. fake-pg에서 장애를 만들 수 있다는 것과 payment가 실제로 복구한다는 것은 구분한다. 먼저 한 거래에 장애 확률 1로 원인을 고정해 정합성을 확인하고, 이후 0·1%·10% 확률 부하를 같은 입력 조건으로 비교한다. 시나리오 5·7의 환불에도 4e·4f를 재사용한다.

설정은 `PUT /fake/admin/faults/{provider}/{operation}`으로 적용한다. `provider`는 TOSS·KAKAO, `operation`은 CONFIRM·CANCEL·INQUIRE이며 카카오 준비는 READY다. 각 실험 전 기존 설정을 초기화하고 전체 설정 JSON을 보관한다. PUT에서 생략한 항목은 이전 값 유지가 아니라 장애 없음 기본값으로 바뀐다.

| 번호 | 상황·설정 예시 | fake-pg에서 확인할 사실 | payment의 기대 결과·측정 |
|---|---|---|---|
| 4a | 처리 전 실패: CONFIRM `serverErrorRate=1` | 승인 기록이 생기지 않음 | 클라이언트는 5xx만으로 미처리 사실을 단정하지 않는다. Unknown으로 받아 조회·유예 규칙으로 확정한다. 중복 승인·유예 전 조기 NOT_APPROVED 없음 |
| 4b | 업무 거절: CONFIRM `failRate=1` | 정상적인 승인 거절과 PG 거절 상태 | FAILED·REJECTED 분류, 승인 자동 재시도 없음, PG 원본 코드 보존. 4a·4c와 실패 의미를 구분 |
| 4c | 승인 후 응답 유실: CONFIRM `responseLossRate=1`, `holdMs`는 클라이언트 read timeout보다 길게 | 실제 승인·금액은 기록됐으나 호출자는 성공 응답을 못 받음 | IN_PROGRESS에서 조회로 DONE 확인. 1분 안에 확인하지 못해 FAILED가 되면 늦은 승인 대사·AUTO_VOID로 해소. 과금·환불 중복 없음 |
| 4d | 늦은 승인: CONFIRM `delayedApprovalRate=1`, `delayedApprovalMs=70000`, 충분한 `holdMs`. PG_UNRESOLVED 검증 시 INQUIRE 장애도 명시 | 처음에는 승인 전 상태이며, 승인 요청 1분 이후 실제 승인됨 | 1분 시한 뒤 FAILED·PG_UNRESOLVED, 이후 승인은 DONE으로 되살리지 않고 AUTO_VOID. 최종 PG 순수취액과 예매 결과 대조 |
| 4e | 환불 처리 전 일시 실패: CANCEL `serverErrorRate=1` 또는 처리 한도 초과 | 승인 금액이 그대로 있고 취소는 미처리 | 환불 REQUESTED 유지·같은 키 재시도. 장애 해제 후 DONE. 장애가 차단 시한을 넘으면 경보·관리자 재처리로 추적 |
| 4f | 환불 후 응답 유실: CANCEL `responseLossRate=1`, 충분한 `holdMs` | PG는 이미 취소됨 | REQUESTED 복구 후 DONE. 토스는 같은 멱등 키 결과 재현, 카카오는 이미 취소됨 오류 뒤 조회로 확인. 실제 취소 1회 |
| 4g | 조회 장애: INQUIRE `serverErrorRate=1` 또는 read timeout보다 긴 `latencyMs` | 승인·취소 사실과 별개로 조회만 실패 | 결제의 1분 확정 규칙과 이후 대사 확인, 환불은 결과 불명만으로 DONE·업무 거절 FAILED로 바꾸지 않음. 조회 복구 뒤 실제 PG 상태로 해소 |
| 4h | 환불 업무 거절: CANCEL `failRate=1` | 취소 거절, PG 승인 금액은 남음 | 환불 FAILED·차단·경보. 장애 해제 후 관리자 retry가 새 키 세대로 처리하며, 같은 키의 거절 재현과 구분 |

현재 responseLossRate는 실제 TCP 연결 절단이 아니라 처리·저장 후 응답을 붙잡았다가 500을 반환하는 모사다. 짧은 holdMs로 500 응답만 받은 실험과 실제 HTTP read timeout을 겪은 실험을 구분해 적는다. 처리 전 접속 실패는 이 설정으로 만들 수 없으며, 별도 네트워크 차단·대상 중지 등 인프라 제어를 준비한 뒤 검증한다. PG 전체 중지와 INQUIRE만의 장애도 구분한다.

### 1분 경계와 늦은 결과 검증

- 단위 테스트는 제어 가능한 시계로 `approve_requested_at + 59초`와 `+60초`를 검사한다. 단순 sleep으로 정확한 경계 검증을 대신하지 않는다.
- HTTP·잡 통합 시험은 실제 PG 호출 시각·실패 확정 시각·잡 주기를 함께 기록한다. 60초 판정 경계와 스케줄러 실행 지연을 구분하고, 허용 지연을 실행 전에 정한다.
- 4d에서 승인 전 상태 조회를 NotFound로 볼지 Unknown으로 볼지는 PG 어댑터 계약에 따른다. NOT_APPROVED 유예 분기와 PG_UNRESOLVED 분기를 섞지 않는다. PG_UNRESOLVED를 목표로 하는 실험은 INQUIRE 장애도 명시해 결과 불명 상태를 유지한다.
- 59초 부근 승인·60초 이후 승인과 계속 조회 불명인 경우를 나눠 실행한다. 복구·요청 경로·대사가 같은 승인을 발견해도 환불 행과 실제 취소는 중복되지 않아야 한다.
- 같은 예매의 order-A가 실패한 뒤 order-B로 다시 결제하고 A가 늦게 승인되는 흐름도 검증한다. A만 자동 환불하고 B의 결제·예매·쿠폰을 변경하지 않는다. 단독 환경은 결제별 금액만 검증하고 예매·쿠폰은 전체 연결에서 확인한다.

### 장애 재현 방식과 준비 상태

| 방식 | 현재 지원·준비 상태 | 사용 목적 |
|---|---|---|
| PG·동작별 전역 확률 및 지연 | fake-pg 설정으로 지원. 해당 결제 흐름·복구 구현 후 통합 측정 | 단일 장애 확률 1 검증, 이후 확률 부하 |
| 특정 orderId에 장애 지정 | 추가 구현 필요. 현재 관리 API의 기능으로 보고하지 않음 | 여러 거래를 동시에 실행하면서 대상 거래만 재현 |
| 첫 취소 응답 유실 → 재시도·조회 성공 같은 단계별 시나리오 | 추가 구현 필요. 현재는 단일 거래·격리 환경에서 설정 전환으로 검증 | 재시도 횟수별 장애·복구 경로 재현 |
| 시드·거래 ID 기반 장애 선택 | 추가 구현 필요. 현재 Random은 실행마다 달라짐 | 같은 입력 거래의 장애 선택을 반복 |
| DB·offset 커밋 사이 강제 종료 | 테스트 제어 지점 준비 필요. 시나리오 8과 연결 | 종료 지점을 정확히 지정한 재시작 시험 |

시드만 고정해도 동시 요청 순서가 달라지면 거래별 장애가 달라질 수 있다. 재현성 확장은 거래 ID·동작·요청 시도 번호와 시나리오 버전을 연결하고, 동일 업무의 재전달과 새로운 실행 시도를 구분한다. 이 항목은 fake-pg 후속 개선안이며 이번 문서 변경으로 구현된 것이 아니다.

### 실험 실행·기록 순서

1. 정상 설정과 신규 입력으로 기준선을 실행한다. PG·동작별 장애 설정, timeout, 복구·대사 간격, 인스턴스·자원, 입력 데이터 식별자를 기록한다.
2. 4a~4h를 한 번에 하나씩 실행한다. 복합 장애는 개별 결과 확인 후 조합·선택 순서를 명시한다.
3. 확률 시험은 명목 확률과 실제 적용 건수를 함께 기록한다. 장애 선택 시점의 안전한 로그·카운터 등 관측 수단이 없으면 먼저 준비하고, 클라이언트 timeout 수만으로 실제 응답 유실 건수를 추정해 확정하지 않는다. 10% 설정을 정확히 10% 발생 보장으로 해석하지 않는다. PG 도달 요청·멱등 재현·업무 거절 등 어느 집합에서 장애를 셌는지 분모를 적는다.
4. 장애를 해제하고 복구·대사 관찰 기간을 둔다. 주입 중과 해제 후 미완료 건수·금액, 최종 해소 시각을 구분한다. 모든 결제의 24시간 대사 확인을 완료하지 않았다면 남은 관찰 구간을 적는다.
5. payment·refund와 fake-pg 거래를 orderId·PG 거래 ID로 대조한다. 기대한 시도만 승인·취소됐는지 확인하고, DLT·차단·결과 불명은 성공 완료로 세지 않는다.
6. 실행 식별자, 코드 커밋, 장애 설정 JSON, 부하 입력, 주입 시각, 거래별 상태 전이·PG 호출·최종 대조 결과를 `docs/payment/perf/`에 저장한다. 인증값·비밀키는 포함하지 않는다. 같은 orderId를 재사용할 때는 의도한 멱등 시험인지 명시한다.

### 시나리오 8의 종료 지점과 예상 결과

아래 지점은 해당 구현 Task의 필수 완료 조건이다. Outbox는 Task 16, Inbox·워커는 Task 16-1에서 검증하며 MVP의 직접 실행 경쟁은 Task 8~10에서 먼저 검증한다.

|---|---|---|
| 업무 상태·Outbox 커밋 후 발행 전 | Outbox에서 재발행한다 | Task 16 필수 |

## 정합성 필수 검증 행렬

아래는 [reliability.md](reliability.md)의 구현 관문이다. 기존 확률 부하 시험만으로 대신하지 않는다. 단계별 중단은 래치·테스트 제어 지점·제어 가능한 시계로 만들고, 실제 HTTP·프로세스 종료 시험과 포트 픽스처 시험을 구분한다. 재현 장치가 없으면 준비 미완료로 남긴다. 계약이 필요한 행은 합의 후 전체 연결에서 검증한다.

시험 기록은 위험 ID → Task → 실행한 테스트/실험과 커밋 → 초기 상태·중단 지점 → 재개 후 DB·PG·예매 대조 → 미실행/잔여 위험 순서로 남긴다. 새 테스트 이름·테이블 구조는 구현할 때 정하며 지금 존재한다고 가정하지 않는다. R10~R12 전체 연결이 미완료이면 Task 12-1·전체 Saga는 미완료다.

| 알려진 미환불 금액 / PG 조회 불명 금액 | 실제 승인·미취소가 확인된 금액과 외부 결과를 아직 모르는 금액을 구분한다 |
| 점유 만료·재인수 / DB 연결 대기 / PG별 활성 호출 | 역할 분리의 효과와 남은 공유 자원 병목을 확인한다 |
| 다른 orderId 시도의 일시적 복수 과금 건수·금액·노출 시간 | PG_UNRESOLVED 재결제 후 이전 시도 과금이 해소되는 과정을 확인한다 |

거래 ID는 로그·추적에 사용하고 paymentId·orderId·eventId를 메트릭 label에 넣지 않는다. 인증값은 로그·실행 이력·DLT에 평문으로 남기지 않는다. 지표 이름과 구현은 해당 작업에서 정한다.

## 성공 기준

숫자는 실측으로 채우고, 아래 기준을 만족했는지를 결과마다 적는다.

| 실험 | 성공 기준 |
|---|---|
| 중복 결제 승인 (동시 요청, 재전송) | 주문당 중복 과금 0건 |
| PG 응답 유실·늦은 승인 | 60초 경계에서 올바른 시한 판정을 하고 실제 실행 지연을 기록한다. 서버 중지·적체 중 1분 내 완료를 보장한다고 보고하지 않는다. 복구·대사 후 FAILED인데 PG 승인 상태로 남은 건 0, 최소 대사 이후 잔여 위험은 R07에 기록 |
| Kafka 소비자 중복 처리 | 환불·확정 실패 보상 명령과 결과 이벤트가 중복돼도 이중 환불·예매 상태 역전 없음. 승인 중복은 HTTP 멱등 시험으로 별도 검증 |
| payment 강제 종료 | 종료 시점의 미완료 거래가 복구 대상에서 빠지지 않는다 (재시작 후 결제는 전부 확정, 환불은 확정 또는 차단) |
| 환불 PG 장애 | 환불 요청이 REQUESTED로 남아 장애 해제 후 끝까지 처리된다 |
| 예매 확정 실패 | 일시 실패는 재확정, 영구 불가는 영속 CONFIRM_FAILED 보상으로 재개된다. 승인된 금액은 환불되거나 담당·금액·재처리 근거가 있는 조치 대상으로 남는다. 로그만으로 보상 완료를 세지 않는다 |
| 워커 종료·중복 인수 | 미완료 작업 누락·중복 과금·중복 환불이 없으며 기존 워커의 늦은 결과도 상태를 역전시키지 않는다 |
| 환불 역할 분리 | 같은 총 자원에서 조회·승인 지연과 환불 완료 시간을 비교하고, DB 병목·운영 비용까지 포함해 채택 여부를 기록한다 |
| 영속 인계 | DB에 인계된 명령은 PG 완료 전에도 Kafka 처리 위치를 전진시킬 수 있다. 그 뒤 워커를 중단해도 DB 대기·경보로 미완료를 추적하고 재시작 후 이어간다 |

"같은 orderId 중복 과금 0", "다른 시도 일시적 복수 과금", "최종 미해소 0"은 다른 지표다. PG 장애가 길면 실험 시간 안에 모두 자동 해소되지 않을 수 있으므로 아래 항목을 구분한다.

- 실험 종료 시점의 미해소 건수
- 장애 해제 후 복구가 최종 확정한 건수와 걸린 시간
- 결제: 결과 확정 시한으로 FAILED(`PG_UNRESOLVED`)가 된 건수와 그중 늦은 승인으로 AUTO_VOID된 건수
- 환불: 자동 처리를 포기하고 차단(사람 확인)으로 넘어간 건수

## 결과 서술 구조

시나리오마다 같은 순서로 쓴다: 문제 → 가설 → 실험 설계 → 동기 결과 → 대안 비교(단순한 것부터) → 선택과 근거 → 개선 후 결과 → 포기한 것과 한계. Kafka가 필요 없었던 결과도 측정한 대로 쓴다.

전체 흐름은 "원인을 단독 환경에서 분리해 측정하고 개선한 뒤, 전체 시스템에서 효과가 유지되는지 확인했다"로 묶는다. 가장 강한 근거는 처리량 숫자보다 시나리오 4의 정합성(같은 orderId 중복 과금 0, 복구 후 미해소 0, 다른 시도의 복수 과금 노출 별도 기록)과, 개선으로 얻은 것과 잃은 것을 함께 보여주는 측정이다.
