# 결제·환불 실험 계획

동기 구현의 한계를 측정하고, 개선 전후를 같은 조건에서 비교한다. 구현 규칙은 [plan.md](plan.md), 작업 순서는 [todo.md](todo.md)에 있다.

## 측정 환경 두 가지

개선 효과는 **단독** 환경에서 비교하고, **전체** 환경은 마지막에 효과가 유지되는지 확인하는 데만 쓴다.

| | 단독 (주 실험) | 전체 연결 (보조 실험) |
|---|---|---|
| 경로 | k6 → payment 내부 API → fake-pg | k6 → Gateway → 예매 → payment → fake-pg |
| 띄우는 것 | payment, fake-pg, PostgreSQL, (Kafka), Prometheus·Grafana | 전체 Compose |
| k6 위치 | `ticket-net`에 붙은 컨테이너. 내부 API는 Gateway 라우트와 호스트 포트가 없으므로 `http://payment-service:8084`로 부른다 | 호스트 또는 컨테이너에서 Gateway로 |
| 쓰는 이유 | 바꾼 변수 하나의 효과만 보인다. 다른 팀원 일정·코드와 무관하게 언제든 같은 조건으로 다시 돌린다 | 다른 서비스로 번지는 영향은 전체 연결에서만 보인다 |
| 시점 | 내 구현(Task 12)이 끝나면 바로 | 예매 연동(Checkpoint B)이 안정된 뒤 트러블슈팅 기간 끝에 1~2회 |

단독 환경에서 k6는 예매 대신 `준비 → 결제창 대체 → 승인`을 직접 호출하고, `expiresAt`도 직접 넣는다.

## 측정 규칙

- 측정 환경(머신, 인스턴스 수, 설정값, 단독/전체)을 결과와 함께 기록한다.
- 한 번에 변수 하나만 바꾼다.
- 워밍업 후 3회 측정하고 중앙값을 쓴다.
- 도구는 k6 + Prometheus/Grafana이고, 결과는 `docs/payment/perf/`에 둔다.
- 아래 숫자는 실험 입력값이다. 결과 칸은 실측으로만 채운다.

## 시나리오

| # | 환경 | 상황 | 가설 | 비교 순서 | 핵심 지표 |
|---|---|---|---|---|---|
| 0 | 단독 | 기준선 (PG 50ms, 실패 0) | - | - | 승인 처리량·p95, 조회 API p95 |
| 1a | 단독 | PG 지연 1·3·5초 | 승인 대기가 payment 스레드를 다 잡아 결제 조회 API까지 느려진다 | 타임아웃 조정 → 벌크헤드 → 서킷 브레이커 → Kafka | 조회 API p95, 활성 스레드, 결과 불명 수 |
| 2 | 단독 | PG 처리 한도 초과 (초당 50건, 초과 429) | 동기는 거절이 폭증한다 | 백오프 재시도 → 속도 제한기 → Kafka 부하 평탄화 | 429 수, 성공률, 완료 시간, 소비 지연, 만료 실패(`EXPIRED`) 수 |
| 4 | 단독 | 승인 후 응답 유실 10%, 승인 처리 지연, PG 호출 중 payment 강제 종료 | 복구가 모든 건을 정확히 마무리한다 | 동기 vs Kafka, 대사 | 불명 해소 수·시간, 대사 불일치 수, 이중 결제 수, 늦은 승인 자동 취소 수 |
| 5 | 단독 | 회차 취소 대량 환불 5,000건 | 한 요청으로는 불가하고, 병렬은 PG 한도에 걸린다 | 순차 → 병렬 → Kafka | 완료 시간, PG 거절 수, DLT 수 |
| 1b | 전체 | PG 지연 3초 | 결제 지연이 예매 스레드를 잡아 좌석 조회까지 느려진다 | 개선 전 vs 1a에서 고른 개선 | 좌석 조회 p95, 예매 활성 스레드 |
| 3 | 전체 | payment 30초 중지 | 동기는 예매의 승인 요청까지 실패한다 | 동기 vs Kafka | 장애 구간 승인 요청 성공률, 복구 시간, 미보상 수 |
| 6 | 단독 | 정산 100만 건 (확장) | - | 전체 읽기 → 청크, 인덱스 | 배치 시간, 재실행 결과 동일성 |

0·1a·2는 MVP 안에 동기 버전으로 측정해 기준선을 확보한다. 1b와 3은 다른 서비스에 의존하므로, 일정이 밀리면 빼고 단독 결과만으로 정리한다.

## 메트릭

| 메트릭 | 용도 |
|---|---|
| `payment_result_total{result, provider}` | 결과 분포 (done, failed, unknown) |
| `payment_unknown_current` | 지금 결과를 모르는 결제 수 |
| `payment_recovery_blocked_total` | 복구 차단 수 |
| `payment_auto_void_total{cause}` | 늦은 승인·금액 불일치 자동 취소 수 |
| `pg_call_duration{provider, operation}` 히스토그램 | PG 지연 |
| `refund_result_total{result, reason}` | 환불 결과 |
| Resilience4j, Kafka 소비 지연 | 장애 격리·처리량 (트러블슈팅 기간) |

## 결과 서술 구조

시나리오마다 같은 순서로 쓴다: 문제 → 가설 → 실험 설계 → 동기 결과 → 대안 비교(단순한 것부터) → 선택과 근거 → 개선 후 결과 → 포기한 것과 한계. Kafka가 필요 없었던 결과도 측정한 대로 쓴다.

전체 흐름은 "원인을 단독 환경에서 분리해 측정하고 개선한 뒤, 전체 시스템에서 효과가 유지되는지 확인했다"로 묶는다. 가장 강한 근거는 처리량 숫자보다 시나리오 4의 정합성(장애를 넣어도 이중 결제 0, 미해소 0)과, 개선으로 얻은 것과 잃은 것을 함께 보여주는 측정이다.
