- 2026-10-27 보강: 기존 문서에 있는 대응의 누락 조건과 구현 관문을 연결했다. 다른 도메인의 구현이나 외부 PG 보장을 일방적으로 확정하지 않는다.

## 2. 위험별 요구사항

### R01. 준비 재전송·동시 준비·시도 역전

- 기존 대응: orderId 멱등 비교, 활성 결제 부분 UNIQUE, 이전 READY의 SUPERSEDED 처리.
- 남는 문제: 원격 준비 후 예매의 조건부 저장만 하면 결제는 B, 예매는 A를 현재 시도로 남길 수 있다. orderId를 먼저 저장해도 오래된 A의 원격 호출이 B보다 늦게 도착하면 B를 대체할 수 있다. 결제 DB의 UNIQUE만으로 서비스 간 순서는 맞춰지지 않는다.
- 필수: 같은 시도의 재시도와 새 준비를 구분한다. 예매와 준비 직렬화·영속 준비 점유 또는 시도 세대 검증 중 방식을 합의한다. 타임아웃·재시작 이후 오래된 실행의 처리도 포함한다. 새 요청 필드·오류를 일방 추가하지 않는다.
- 필수: 카카오 READY의 tid 없는 재개를 동시에 실행하거나 tid 응답이 늦게 도착해도 현재 시도·확정 상태를 덮지 않는다. 대체·만료된 시도에 준비 URL을 뒤늦게 저장해 사용 가능 상태로 되살리지 않는다.
- 연결: Task 1-1·7·12-1. 결제 단독 충돌 시험과 전체 연결 순서 역전 시험을 모두 통과한다.

### R02. 준비 실패와 금액 신뢰 경계

- 기존 대응: 음수 할인·최종 100원 미만 거절, 할인액까지 matches 비교, 쿠폰은 예매 소유.
- 필수: 결제 준비의 HTTP 200 + FAILED(READY_FAILED)를 예매가 준비 성공으로 반환하지 않게 계약 DTO·어댑터 매핑을 확인한다. 실패 상태 전달 또는 명시적 업무 예외 매핑을 합의하고 시험한다.
- 필수: 예매는 티켓 가격·쿠폰에서 서버 계산한 정가·할인액을 보낸다. 결제의 산술 검증이 쿠폰 권한 검증을 대신한다고 해석하지 않는다. 금액 정수 범위·음수·초과 할인 경계를 검증한다.
- 연결: Task 1-1·7·12-1.

### R03. 승인 중복·인증값 재사용·만료 경쟁

- 기존 대응: 잠금 후 READY 확인, 요청 금액 대조, PG 거래 ID UNIQUE, 호출 직전 만료 검사.
- 필수: 승인 접수와 실제 실행을 구분한다. 잠금 대기 뒤 상태·만료를 다시 읽고, 중복 요청이 실행 중 결제를 실패로 바꾸지 않는다. 승인 접수된 READY를 새 준비가 대체하지 않는다.
- 한계: 호출 직전 검사를 통과한 프로세스가 장시간 멈췄다가 PG를 호출하는 가능성까지 DB 잠금으로 제거할 수 없다. R07의 지연 실행·PG 보장 확인과 대사로 다룬다.
- 연결: Task 7·8·12.

### R04. 외부 응답의 거래 정체성·금액 검증

- 기존 대응: 어댑터의 Approved / Rejected / Unknown 분류와 승인액 불일치 AUTO_VOID.
- 필수: PG가 제공하는 필드 기준으로 기대 거래 ID·주문 연결·금액·상태를 검증한다. 통화·가맹점 정보가 제공되면 함께 대조하고, 제공되지 않는 필드는 검증 불가와 대체 확인 경로를 문서화한다. 가짜 성공 JSON의 누락·타 거래·비정상 금액을 무조건 성공으로 취급하지 않는다.
- 필수: 취소 성공·기취소 조회는 전액 취소 여부와 확인 가능한 실제 취소액을 대조한다. 부분 취소·불일치가 발견되면 현재 전액 환불을 DONE으로 숨기지 않고 불명·조치 대상으로 추적한다. 실제 과금이 확인된 금액 불일치는 ensureRefund로 보상한다.
- 연결: Task 6의 추가 보완·8·10·21. 결과 타입·스키마 확장이 필요하면 먼저 설계하고 실제 변경과 함께 tables.md를 맞춘다.

### R05. 전송 실패·응답 유실·커밋 실패

- 기존 대응: 보낸 뒤 실패·5xx는 Unknown, 먼저 IN_PROGRESS 저장, 조회 기반 복구, 승인 자동 재시도 없음.
- 필수: PG 성공 후 DB 결과 저장 실패, DB 결과 저장 후 HTTP 응답 유실, 상태 저장 후 PG 호출 전 종료를 각각 시험한다. 예매는 결과를 모른다는 이유로 좌석을 풀지 않는다.
- 필수: 429의 미처리 보장은 fake-pg 가정이다. 실제 PG 보장을 확인하기 전에는 실제 연동에서 미승인으로 단정하지 않는다.
- 연결: Task 6·8·9·12·21.

### R06. 1분 종료와 일시적 복수 과금

- 기존 대응: PG_UNRESOLVED로 시도를 닫고 늦은 승인은 AUTO_VOID. 예매는 기존 좌석 만료 정책에 따라 HOLD 복귀 또는 EXPIRED.
- 필수: FAILED는 모든 경우에 미과금을 증명하지 않는다. A가 시한 종료된 뒤 B로 결제하고 A가 늦게 승인되는 시험에서 A만 환불하고 B·현재 티켓·쿠폰을 보존한다.
- 필수: 같은 orderId 중복 승인 0과 서로 다른 시도의 일시적 복수 과금은 다른 지표다. 복수 과금 건수·금액·노출 시간과 최종 미해소 금액을 따로 기록한다. 고객 안내의 표현은 예매 담당과 합의한다.
- 한계: 현재 정책은 늦은 과금의 최종 해소를 목표로 하며 순간적인 복수 과금·한도 점유까지 0으로 보장하지 않는다.
- 연결: Task 1-1·9-1·11·12·12-1.

### R07. 대사 시점·늦은 실행·증명되지 않은 PG 보장

- 기존 대응: PG 호출 대상 FAILED를 실패 확정 11분·24시간 뒤 최소 대사. Unknown이면 체크포인트를 소비하지 않음.
- 필수: 인증 유효 시간 종료를 이미 접수한 PG 요청의 완료 불가능 증거로 사용하지 않는다. 장시간 프로세스 정지 뒤 호출, 조회 반영 지연, 마지막 대사 이후 늦은 승인 가능성을 위험으로 남긴다.
- 필수: 최소 대사는 최종 누락 부재의 증명이 아니다. 체크포인트별 점유·재시작·중복 실행·Unknown 재조회와 reconciled_at → reconcile_count·next_reconcile_at 이전을 검증한다.
- 필수: 실PG 운영 전 승인 유효 시간·처리 최대 지연·조회 정합성·멱등키 범위를 공식 계약·샌드박스로 확인하고, 확인 불가 항목은 운영 제한·추가 대사와 담당을 정한다.
- 연결: Task 9-1·12·19·21·21-1.

### R08. 1분 판정과 복구 잡의 실행 용량

- 기존 대응: 결제 10초 조회, 후보별 예외 격리, 짧은 점유 트랜잭션.
- 필수: 60초는 판정 기준이지 서버 중지·DB 장애·스케줄러 적체 중에도 보장되는 완료 시간이 아니다. 59/60초 로직 경계와 실제 판정 실행 지연을 따로 측정한다.
- 필수: 오래 걸리는 PG 조회가 한 묶음을 막는 시험, 후보가 계속 들어오는 공정성, 복구 밀림·최고 대기 나이·조회 예산을 검증한다. 순차 50건 × 조회 10초면 약 500초가 걸릴 수 있으므로 설정 주기를 실제 처리 주기로 간주하지 않는다.
- 연결: Task 9·11·12·14·15-1·18.

### R09. 점유 만료·다중 실행·오래된 결과

- 기존 대응: 점유 시각 갱신, 상태 잠금 재확인, PG 멱등성·카카오 기취소 조회.
- 필수: 재인수 뒤 기존 호출은 살아 있을 수 있다. 환불 cancel_attempt와 실행 소유·세대 등으로 오래된 결과의 최신 상태 덮어쓰기를 막는다. 구체 필드는 구현 때 정한다.
- 필수: 이전 취소 세대의 늦은 거절이 새 세대 성공을 실패로 바꾸지 않는다. 늦은 성공은 무조건 버리지 않고 PG 조회·금액 검증으로 확인한다. 승인 성공은 FAILED를 되살리지 않고 필요한 보상으로 연결한다.
- 연결: Task 8·9·10의 기본 경쟁 시험, Task 15-1·16-1의 종료·재인수 시험. 워커 분리 전에도 현재 실행 경로의 경쟁 안전성은 필수다.

### R10. 예매 확정 실패의 보상 의도

- 기존 대응: 예매가 결제 결과를 재조회하고 확정을 재시도하며 F6 로그·지표를 남김.
- 필수: 일시 DB 장애·잠금 실패는 확정 재시도, 영구 확정 불가는 보상으로 구분한다. 영구 불가를 무기한 PAYMENT_IN_PROGRESS로 재시도하거나 모든 예외를 즉시 환불하지 않는다.
- 필수: 과금된 orderId와 CONFIRM_FAILED 보상 의도를 예매가 영속 저장하고 재시작 후 재요청한다. 보상 접수 후 PG 환불은 결제가 책임진다. 오래된 시도만 환불하며 현재 시도를 건드리지 않는다.
- 상태: booking-decisions.md B19의 MVP 로그·지표만 남기는 범위와 차이가 있다. 예매 담당과 우선순위를 합의해야 하며, 합의 전 예매 구현을 임의 변경하지 않는다. 로그만으로 Saga·전체 MVP 정합성 완료를 선언하지 않는다.
- 연결: Task 1-1·10·12-1·Checkpoint C. Kafka 전환까지 보상 자체를 미루지 않는다.

### R11. 취소 접수·PG 취소·실제 금액 반환의 구분

- 기존 대응: 예매 CANCELING 저장 후 환불 요청, 접수 확인 후 CANCELED. 결제 환불 WAITING·REQUESTED도 인수된 작업.
- 필수: 예매의 취소 의도 저장·요청·접수 응답·CANCELED 저장 각각의 중단을 재시도한다. 접수 전에 정책상 거절한 경우와 접수한 환불의 PG 실행 실패를 구분한다.
- 필수: 접수 후 PG 실패로 취소 확정 예매·티켓을 CONFIRMED로 되살리지 않는다. refund FAILED·차단·DLT는 미완료 환불 책임을 종료하지 않는다.
- 필수: refund DONE은 현재 모델의 PG 취소 성공이며 실제 계좌·카드 반영 완료를 증명하지 않는다. 접수 응답 지연과 PG 완료 지연을 구분한다. MVP의 커밋 후 최초 PG 시도는 유지하고, PG 호출을 응답 경로에서 완전히 떼는 비교는 Task 15-1에서 한다.
- 연결: Task 1-1·10·10-1·12-1·15-1.

### R12. 좌석·쿠폰의 로컬 원자성과 이전 시도 격리

- 기존 대응: 좌석 → 예약 잠금 순서, 예약 ID 일치 조건, CouponUsage의 예매 트랜잭션 참여.
- 필수: 확정과 좌석 판매·쿠폰 사용, 취소 확정과 좌석 반환·쿠폰 복원이 한 로컬 트랜잭션에서 함께 성공하거나 롤백한다. PAYMENT_IN_PROGRESS의 좌석·쿠폰을 만료 작업이 임의 반환하지 않는다.
- 필수: FAILED → HOLD 때 쿠폰 유지, EXPIRED·RELEASED 때 해제, CANCELED 때 복원, 이전 orderId AUTO_VOID는 현재 쿠폰에 영향 없음을 시험한다. 좌석 갱신 수 부족·쿠폰 영구 오류는 R10으로 연결한다.
- 한계: 쿠폰을 별도 서비스로 옮기면 인터페이스 교체만으로 기존 원자성을 보존할 수 없다. 새 분산 계약·복구가 필요하다.
- 연결: Task 1-1·12-1. 쿠폰 초안 #27·좌석 계약의 미합의와 구현을 구분한다.

### R13. Kafka 인계·중복·역순·실패 메시지

- 기존 대응: 생산자 Outbox, Inbox와 영속 작업 원자 저장 후 offset 커밋, eventId·orderId 멱등.
- 필수: 발행 ACK 유실, DB/offset 사이 종료, 다른 eventId의 같은 업무, 오래된 시도·세대의 결과를 시험한다. 같은 파티션 key만으로 재발행·재처리·다른 시도의 업무 역전을 해결한다고 보지 않는다.
- 필수: Kafka 발행 성공·결제 DB 접수·PG 성공을 구분한다. 예매의 CANCELED 전환은 합의한 결제 접수 확인 기준을 따른다. 최종 결과 이벤트만으로 PG 완료까지 기다리게 만들거나 Kafka 발행만으로 결제 접수를 단정하지 않는다. 필요한 접수 통지·조회 방식을 별도 합의한다.
- 필수: DLT는 운영 추적·경보·재처리·금액 대조 대상이다. 메시지를 옮겼다는 이유로 환불을 완료로 세지 않는다.
- 연결: Task 1-1·15·16·16-1·17·18.

### R14. 대량 환불·포화·일반 요청 보호

- 기존 대응: 제한된 병렬 처리, 환불·복구 풀 분리, 필요 시 프로세스 분리, 합산 PG 한도.
- 필수: 승인·취소·조회가 공유하는 PG 예산을 확인하고 조회·복구 자원을 확보한다. 큐의 용량·최대 대기·포화 시 거절 또는 영속 대기 정책을 정한다. 이미 인수한 환불은 버리지 않는다.
- 필수: 순차 HTTP → 제한 병렬 HTTP → Kafka 직접 소비 → Inbox·워커를 같은 총 자원·PG 한도에서 비교한다. 병렬화 효과를 Kafka 단독 효과로 보고하지 않는다.
- 한계: PG·DB 한도가 같으면 Kafka가 완료 TPS를 무조건 높이지 않는다. 접수 지연, 일반 승인·조회 보호, 장애 후 재개, 최종 완료 시간을 각각 평가한다.
- 연결: Task 13~18.

### R15. 이력·미완료 목록·운영 인수

- 기존 대응: 상태·recovery_attempts·last_error·지표와 환불 관리자 retry/unblock 계획.
- 필수(MVP): 상태 변경과 관리자 재시도의 이전/이후 상태·대상 orderId/paymentId·cancel_attempt·시각·작업자·사유·확인한 PG 결과를 영속 추적한다. 단순 현재 상태와 마지막 오류만으로 복원할 수 없는 중요한 전이를 남긴다. 구체 이력 저장 형식·트랜잭션은 Task 10-1에서 정하고 DDL 변경과 함께 문서를 갱신한다.
- 필수(MVP): REQUESTED 차단·FAILED·장기 WAITING·미해소 보상 목록과 건수·금액·가장 오래된 나이, 담당·확인 주기·경보·재시도·종료 근거를 운영 절차로 둔다. 별도 운영 UI 대신 내부 조회나 승인된 운영 쿼리로 시작할 수 있다.
- 필수(운영 전): 전체 PG 호출 시도 이력·보관 기간·비밀값 제거·대사 증거와 운영 인수 절차를 보강한다. 로그만 보고 수동 상태를 덮어쓰지 않는다.
- 연결: Task 10-1·11·12·21-1.

### R16. 내부 호출·관리자 권한·민감정보

- 기존 대응: Gateway의 /internal 차단, 사용자 소유권 검사 원칙, 인증값 로그·응답·이벤트 제외.
- 필수(MVP): 내부 API·관리자 경로의 호출 주체와 접근 경계를 문서화하고 무권한 접근 거절을 시험한다. 관리자 경로는 네트워크에 있다는 이유만으로 신뢰하지 않는다. 헤더 위조 가능성과 실제 배포 노출을 점검하고 인증·네트워크 통제의 조합을 플랫폼 담당과 합의한다.
- 필수: PG 오류 본문·준비 URL·예외·이력·DLT까지 인증값·키 유출을 검사한다. 실제 비밀 파일은 시험 산출물에 포함하지 않는다.
- 연결: Task 1-1·7·8·10-1·12·21-1. 새로운 공통 인증 계약은 합의 후 구현한다.

### R17. 외부에서 달라진 거래·전체 대사·웹훅

- 기존 대응: FAILED 최소 대사. 전체 대사는 확장 Task 19.
- 필수(운영 전): DONE·CANCELED·refund DONE을 포함한 내부 기록을 PG 거래 내역과 비교한다. PG 콘솔 취소·부분 취소·상태 불일치·내부에 없는 거래를 찾고 예매 티켓 위험과 연결한다. 외부 자료가 없으면 커버리지 한계를 적는다.
- 필수(운영 전): 사용하는 PG의 웹훅 지원을 확인하고, 도입 시 해당 PG의 공식 진위 확인·재조회 절차, 중복·역순·유실 복구를 설계한다. 모든 PG에 같은 서명 방식이 있다고 가정하지 않는다. 외부 공개 경로·인증·메시지 계약은 합의 후 만든다. 웹훅은 전체 대사를 대체하지 않는다.
- 연결: Task 19·21·21-1. 프로젝트에서 생략하면 실과금 운영 준비 미완료로 남긴다.

### R18. 배포·스키마 변경·백업 복원

- 필수(운영 전): create로 실제 거래를 초기화하지 않고 버전 관리한 스키마 변경·이행·롤백 절차를 둔다. 대사 컬럼·이력·Outbox·Inbox 추가 시 미완료 작업이 이전/새 버전에서 누락되지 않게 한다.
- 필수(운영 전): DB 복원 후 이미 PG에서 처리된 거래·발행된 메시지를 다시 만날 수 있음을 시험한다. PG 재조회·멱등 키·이력·대사로 맞추고, 복원된 오래된 상태에서 무조건 신규 과금·환불하지 않는다. RPO/RTO와 복구 후 대사 범위·재개 승인자를 기록한다.
- 연결: Task 9-1·16의 변경별 마이그레이션 검토, Task 21-1의 운영 복구 훈련.

## 3. Saga 완료 관문

예매가 전체 흐름을 조정하고 결제는 PG 실행·환불 책임을 가진다. 별도 saga 테이블이나 Kafka 도입 자체는 완료 조건이 아니다. 기존 상태와 영속 보상 기록으로 아래를 증명하면 된다.

- 진행 상태와 다음 작업을 재시작 후 찾는다.
- 일시 실패는 재시도하고 영구 확정 불가는 보상한다.
- 보상 요청·접수·결과 유실을 멱등 재개한다.
- 취소 접수 후 PG 실패가 이미 취소된 티켓을 되살리지 않는다.
- 좌석·쿠폰의 로컬 변경은 원자적이며 이전 결제 시도를 현재 시도와 구분한다.
- 자동화가 멈춰도 미완료 금액과 운영 담당이 남는다.

**로그·지표만 남기는 F6는 보상 완료가 아니다.** 예매와 R10·R11을 합의하고 Task 12-1을 통과해야 전체 Saga 완료라고 보고한다. 결제 단독 포트 시험은 해당 서비스의 검증이며 실제 좌석·쿠폰·예매 연결의 대체 증거가 아니다.

## 4. 근거와 남은 합의

- 준비 순서·고객 안내·영구 확정 실패 판정·보상 의도 저장·취소 접수 확인·Kafka 접수 통지는 결제와 예매가 Task 1-1에서 합의한다. 실행 풀·내부 인증은 플랫폼, 좌석·쿠폰 원자성은 해당 담당을 포함한다.
- 기존 계약과 다른 필드·오류·상태·이벤트가 필요하면 계약 이슈 → 합의 → docs/shared 계약 PR → 구현 순서를 따른다. 이 문서의 대안은 합의된 wire 계약이 아니다.
- [Saga](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga), [보상 트랜잭션](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction): 보상 진행을 저장하고 멱등 재개·운영 인수가 필요하다.
- [토스 멱등성](https://docs.tosspayments.com/blog/what-is-idempotency), [웹훅](https://docs.tosspayments.com/guides/v2/webhook): 실제 PG의 보장 범위는 해당 연동 버전에서 확인한다.
