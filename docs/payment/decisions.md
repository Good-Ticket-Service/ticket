# 결제·환불 설계 결정

[plan.md](plan.md)의 규칙이 왜 그런지 적는다. 결정마다 결정, 대안, 대가를 둔다. 규칙 자체는 plan.md에만 있고, 여기서는 이유만 다룬다. 구현이 끝난 결정은 ADR로 옮겨도 된다.

이전 프로젝트(물류 MSA)의 Hub 멱등 재고와 Orders 결과 불명 복구는 이미 구현했다. 이번 질문은 같은 원리를 **통제할 수 없는 외부 시스템(PG)과 실제 돈**에 적용할 때 무엇이 달라지는가이다.

## D1. 응답 없음은 실패가 아니라 "모름"이다

- 결정: PG 결과를 `Approved / Rejected / Unknown`으로 강제하고, 처리됐을 가능성이 있는 응답은 모두 Unknown으로 둔다 (plan.md 6절 분류표).
- 대안: 타임아웃 = 실패. 구현은 단순하다. 하지만 실제로 승인된 결제를 실패로 보고 사용자가 다시 결제하면 이중 결제가 되고, 좌석을 풀면 "돈만 빠짐"이 된다.
- 대가: Unknown을 마무리할 조회 API와 복구 잡이 반드시 있어야 한다.
- Rejected는 "확실히 승인되지 않았다"일 때만 쓴다. TCP 연결 단계 실패와, PG 계약상 미처리가 보장되는 429만 Rejected로 둔다. 사용자가 바로 다시 시도할 수 있어야 하기 때문이다. 실제 토스의 429가 그 보장을 하는지 확인하기 전까지 실제 PG 어댑터는 429를 Unknown으로 둔다. 다만 Feign은 연결 실패와 읽기 타임아웃을 같은 예외로 감싸므로, 어댑터가 원인 예외로 구분하지 못하면 Unknown으로 둔다. 잘못 Rejected로 분류하면 사용자가 다시 결제해 이중 결제가 된다.

- FAILED라도 예매가 할 일은 다르다. 업무 거절이면 다른 수단으로 다시 결제하고, PG 일시 장애면 잠시 후 같은 수단으로 다시 시도한다. 그래서 응답에 `failureType`(REJECTED / UNAVAILABLE / EXPIRED / NOT_APPROVED / CLOSED)을 싣고, 내부 표준 코드(`failure_code`)와 PG 원본 코드(`pg_failure_code`)를 나눠 저장한다.

## D2. 외부 PG는 재전송이 아니라 조회로 확정한다

- Hub는 우리가 만든 멱등 API라 같은 요청을 다시 보내면 최초 결과가 재현됐다.
- 외부 PG에 승인을 다시 보내면 "이미 처리됨" 오류가 오거나 PG마다 동작이 다르다. 카카오의 `pg_token`은 일회용이고 payment는 인증값을 저장하지 않는다. 그래서 복구는 주문번호로 **조회**해 확정한다.
- 조회의 "승인 기록 없음"은 바로 거절이 아니다. 승인 요청이 아직 PG로 가는 중이거나(서버 지연, 커넥션 대기) PG 안에서 늦게 처리될 수 있다. 승인 호출 후 유예 시간(1분)이 지나야 거절로 확정한다. 유예 뒤에 승인되는 드문 경우는 최소 대사(D12)가 돌려준다.
- 대가: PG 어댑터마다 조회 API를 구현해야 하고, fake-pg도 조회와 "승인 처리 지연"을 지원해야 한다. 유예 시간 동안 결과가 확정되지 않으므로 사용자는 "결제 확인 중"을 더 오래 볼 수 있다.

## D2-1. 결제는 준비와 승인 두 번의 요청이다

- 결정: 결제 요청을 준비(checkout)와 승인(confirm)으로 나눈다 (plan.md 4절).
- 이유: 두 PG 모두 승인에 사용자 인증 결과가 필요하다. 토스는 결제창을 띄우려면 `orderId`·`amount`가 먼저 있어야 하고 인증 후 `paymentKey`가 온다. 카카오는 서버가 준비 API로 `tid`를 받아야 결제창을 띄울 수 있고 인증 후 `pg_token`이 온다. 한 번의 요청에 인증값을 담는 방식은 두 PG 모두에서 성립하지 않는다.
- 얻는 것:
  - READY가 "금액 확정, 인증 대기"라는 분명한 뜻을 가진다.
  - 승인 직전에 만료를 확인해, 시간이 지난 결제는 PG를 부르지 않는다. 돈이 오가기 전에 막으므로 보상 환불이 생기지 않는다. Kafka 전환 후 줄에서 기다리다 만료된 승인도 같은 관문에서 걸린다.
  - 승인 요청의 금액을 저장된 금액과 대조해 위변조를 막는다(토스 문서가 요구하는 검증).
- 대가: 내부 API가 하나 늘고, 사용자가 결제창을 닫은 READY를 만료 시각에 정리해야 한다. PG를 바꾸거나 재시도할 때는 새 준비가 이전 READY를 대체한다.
- READY의 뜻이 "승인 요청이 아직 안 왔다"와 "왔는데 처리 전이다"(Kafka 대기, 늦은 도착) 둘 다일 수 있다. 그래서 예매는 READY만 보고 HOLD로 되돌리지 않고, 저장한 인증값으로 승인 요청을 다시 보낸다(#9 예매 설계와 같음). HOLD로 되돌린 뒤 늦은 승인이 성공하면 돈은 빠졌는데 좌석이 풀린다.

## D3. 외부 호출은 트랜잭션 밖, 상태는 먼저 커밋

- 결정: IN_PROGRESS를 커밋한 뒤 PG를 부르고, 결과는 새 트랜잭션에 저장한다. 구현은 Orders의 `OrderTransactions`처럼 트랜잭션 전용 bean으로 한다.
- 이유: PG 지연 동안 DB 커넥션을 잡지 않는다. PG 호출 중 서버가 죽어도 IN_PROGRESS가 남아 복구가 찾는다.
- 별도 bean인 이유: 같은 클래스 안의 `@Transactional` 호출은 프록시를 거치지 않아 트랜잭션이 걸리지 않는다. 경계가 클래스 이름으로 드러나고 트랜잭션 단위로 테스트할 수 있다.
- Orders와 다른 점:
  - Orders의 범용 `change(id, Consumer)` 대신 전이마다 이름 있는 메서드를 둔다. 결제는 상태 전이가 핵심이라 메서드 이름이 리뷰 단위가 된다.
  - Orders는 단일 인스턴스를 전제로 메모리 잠금(`ActiveOrderProcessing`)을 썼다. 이번에는 여러 인스턴스로 실험하므로 DB 잠금만 쓴다.
- 대안: `TransactionTemplate` 주입. 경계를 한 메서드 안에서 볼 수 있지만 흐름 코드가 길어지고 트랜잭션 단위 테스트가 어렵다.

## D4. 결과를 모르는 결제는 1분 뒤 FAILED로 끝내고, 늦은 승인은 돌려준다

- 결정: PG 승인을 부른 뒤 1분 안에 결과를 모르면 결제를 FAILED(`PG_UNRESOLVED`)로 확정한다. 예매는 선점 시간이 남으면 HOLD로 복귀해 좌석·쿠폰을 유지하고, 만료·해제 시 반환한다. 결제는 차단하지 않고 관리자 확정(`resolve`)도 두지 않는다. 그 뒤에 승인이 발견되면 결제는 FAILED 그대로 두고 자동 취소 환불(D12)로 돌려준다 (팀 결정, Notion 검토 3-3, 2026-10-26).
- 이유: 결과를 모르는 결제를 IN_PROGRESS로 무기한 붙잡지 않고 1분 안에 해당 시도를 종료해 예매가 재시도 또는 만료 처리를 할 수 있게 한다. HOLD 복귀 시 선점은 원래 만료 시각까지 유지되므로, 결제 실패 확정 시한을 좌석·쿠폰 해제 시한으로 보지 않는다. 늦게 확인된 승인은 자동 환불한다.
- 대안: 시간 한도를 넘기면 IN_PROGRESS + `recovery_blocked`로 두고 관리자가 PG 콘솔로 확인해 확정한다(Orders 방식, 이전 설계). 승인된 결제를 잃지 않지만 좌석이 관리자 처리 전까지 묶인다.
- 대가: 실제로 승인된 결제가 FAILED로 끝날 수 있다. 사용자는 결제 실패를 보고 다시 결제할 수 있고, 처음 결제는 최소 대사가 찾을 때까지(11분 뒤 조회) 돈이 잡혀 있다가 환불된다. 그래서 최소 대사가 MVP 필수다. 예매는 FAILED로 HOLD에 돌아갈 때 쿠폰을 유지한다. EXPIRED·RELEASED 때 해제하며, 늦은 승인 환불에서는 쿠폰을 바꾸지 않는다.
- 1분인 이유: 승인 호출의 최대 대기(connect 2초 + read 10초)보다 충분히 길어, 응답 유실이나 짧은 PG 장애는 조회 몇 번(10초 간격)으로 확정된다. 선점 시간(10분)에 비해 짧아 사용자가 다시 결제할 시간이 남는다.
- 환불은 다르다: 환불은 PG에 이미 돈이 잡혀 있어 "모르니 끝낸다"가 성립하지 않는다. 시간 한도를 넘기면 REQUESTED 그대로 `recovery_blocked`를 켜고, 관리자가 확인한 뒤 차단 해제(`refund/unblock`)로 다시 넣는다. 업무 거절은 새 키 세대로 다시 보낸다(`refund/retry`). Orders의 보상은 내부 재고 복원이라 끝까지 재시도하면 성공했지만, 이번 보상은 실제 환불이라 PG가 계속 거절할 수 있어 자동화의 경계를 차단과 관리자 확인으로 둔다.
- 시간 기준인 이유(환불): 5초 간격 20회 같은 횟수 한도는 PG가 2분만 장애여도 그동안의 환불을 전부 차단한다. 회차 취소 같은 대량 환불에서 짧은 장애는 자동으로 회복되어야 한다.

## D5. 멱등은 세 겹으로 막는다

| 겹 | 키 | 막는 것 |
|---|---|---|
| 내부 API | orderId (결제·환불 모두) | reservation의 재요청 |
| PG 취소 | `orderId:cancel:{cancel_attempt}` 멱등 키 (토스), 조회 후 취소 (카카오) | 우리 재시도로 인한 이중 환불 |
| Kafka 소비 (전환 후) | processed_event | 메시지 중복 전달 |

각 겹은 DB 유니크·부분 유니크 인덱스가 다시 막는다. 애플리케이션 검사가 경쟁 조건에서 뚫려도 DB가 최후 방어선이 된다.

- 환불 키가 예매가 아니라 결제(orderId) 단위인 이유: 늦은 승인처럼 한 예매에 승인된 결제가 둘 생기면 둘째를 따로 환불해야 한다. 예매 단위 키로는 첫 환불이 재현될 뿐이다.
- PG 취소 키에 세대(`cancel_attempt`)를 붙이는 이유: 토스는 같은 `Idempotency-Key`의 응답을 거절까지 15일간 그대로 돌려준다. 결과를 모를 때는 같은 키로 다시 보내 중복을 막고, 업무 거절 뒤 관리자가 다시 시도할 때만 세대를 올려 새 요청으로 보낸다.

## D6. 쿠폰은 예매에서 처리하고 결제는 확정 금액만 저장한다

- #22: 쿠폰 모듈은 reservation-service로 옮긴다. 예약·사용·반납은 예매의 로컬 트랜잭션으로 처리한다.
- 결제 준비 요청은 `totalPrice`와 `discountAmount`를 받는다. 할인액은 0 이상, 최종 금액은 100원 이상이어야 한다. 결제는 할인 정책·쿠폰 유효성을 확인하거나 할인액을 보정하지 않는다.
- `discountAmount`도 orderId 멱등 비교 대상이다. 할인액을 바꾸려면 새 결제 시도가 필요하다.
- 결제는 CouponUsage를 호출하지 않고 쿠폰 ID도 저장하지 않는다. 정가·할인액·결제액은 결제 및 정산 기록으로 남긴다.
- 예매가 결제 결과를 관측해 쿠폰을 처리하므로 PG 결과와 쿠폰 상태 변경은 원자적이지 않다. 예매의 멱등 처리·재조회·복구가 필요하다. #27 제안에 따라 쿠폰은 reservationId에 연결하고 FAILED 후 HOLD 복귀 시 유지한다. EXPIRED·RELEASED 때 해제하고, 환불 접수 후 CANCELED 확정과 같은 로컬 트랜잭션에서 복원한다. 결제·예매 담당은 이 방향에 동의하며 쿠폰 담당 검토는 후속 계약에서 진행한다.
- 이전 orderId의 늦은 결과가 현재 예매·쿠폰 상태를 바꾸지 않도록 예매가 현재 시도를 확인한다. 쿠폰 연결 키를 reservationId로 바꿔도 결제·환불 멱등 키는 orderId다.
- 계약 변경안은 [CouponUsage](../shared/modules/coupon-usage.md)와 [결제 내부 API](../shared/internal-api/payment.md)에 기록한다.

## D7. "어느 PG"와 "언제"를 나눈다

- `PgClient`는 어느 PG를, `PaymentDispatcher`는 지금 처리할지 줄 세울지를 정한다.
- 덕분에 PG 처리 한도 대응(Kafka 워커)이 PG 어댑터를 건드리지 않는다. 동기·Kafka 비교를 설정만 바꿔 같은 코드로 할 수 있어 비교가 공정하다.
- `dispatch`가 `void`인 이유: 결과를 반환하게 만들면 Kafka 구현이 불가능하다.

## D8. PG 자동 전환은 제한한다

- 토스 결과가 불명인 orderId를 카카오로 다시 결제하면, 토스가 실제로 승인했을 경우 이중 결제다.
- 전환을 한다면 서킷이 열려 **아예 호출하지 않은** 새 결제에만 허용한다. 1차는 사용자가 PG를 고르는 것까지만 한다.

## D9. 처리 용량은 시스템 전체로 맞춘다

- PG 처리 한도 × 선점 시간 = 선점 시간 안에 처리할 수 있는 결제 상한 (예: 초당 50건 × 600초 = 3만 건).
- 이를 넘는 결제가 몰리면 대기 중 선점이 만료돼 보상 환불이 쏟아진다. 대기열 입장 속도를 결제 처리 용량에서 역산하도록 대기열 담당과 맞춘다.

## D10. fake-pg는 별도 컨테이너, 샌드박스는 증명용

- 샌드박스는 브라우저 결제 단계가 있어 부하 테스트를 할 수 없고 장애를 주입할 수 없다.
- fake-pg는 네트워크 너머에 있어야 지연·연결 끊김이 실제처럼 생긴다. 공식 API 형식을 따르면 어댑터 하나로 두 환경을 지원한다.
- 테스트 대부분은 포트 픽스처로 빠르게 돌리고, fake-pg 컨테이너는 어댑터 계약과 E2E에만 쓴다.

## D11. DB 인스턴스는 공유, 스키마는 분리

- 서비스별 계정·스키마로 데이터 소유권은 나뉘지만 인스턴스가 하나라 부하·장애는 격리되지 않는다.
- 부하 테스트에서 예매 부하가 결제 지연으로 번지는지 관찰하고, 번진다면 인스턴스 분리의 근거로 삼는다.

## D12. 늦은 승인은 자동으로 취소한다

- 결정: FAILED로 확정한 결제에 PG 승인이 발견되면(요청 경로의 늦은 응답, 복구 조회, 대사) 결제는 FAILED 그대로 두고 자동 취소 환불(`AUTO_VOID`)을 건다. 승인 금액이 저장 금액과 다를 때도 같다.
- 이유: "승인 기록 없음"의 유예 시간과 연결 실패 판단은 확률을 줄일 뿐 0으로 만들지 못한다. 확정 뒤에 승인이 나타나는 경우를 따로 처리하지 않으면, 결과 저장이 "IN_PROGRESS일 때만"이라 승인을 조용히 버리고 돈만 빠진다. 1절 목표("돈만 빠짐 0")는 이 경로가 있어야 지킬 수 있다.
- 환불 행은 결제마다 하나라서, AUTO_VOID는 새 행을 무조건 넣지 않고 `ensureRefund` 하나로 처리한다. 이미 사용자 환불(WAITING·SKIPPED·REQUESTED)이 있으면 그 행을 REQUESTED로 올리거나 그대로 둔다. 그래서 늦은 승인이 어느 시점에 발견되든 유니크 제약에 걸리지 않고 돈을 돌려준다.
- 발견 경로는 셋이다: 요청 경로의 늦은 응답, 복구 조회, 최소 대사. 유예나 결과 확정 시한(D4) 뒤 FAILED가 된 결제는 복구 잡이 더 보지 않으므로, PG 승인을 호출했던 FAILED 결제를 확정 11분 뒤와 24시간 뒤에 조회하는 최소 대사를 MVP에 둔다. 11분은 토스 인증값 유효 시간(약 10분)이 지나 더는 승인될 수 없는 시점이라 첫 조회로 대부분 확정된다. 전체 대사(모든 거래 대조)는 확장 단계다.
- "늦은 승인을 반드시 돌려준다"는 주장에는 끝나는 시점이 필요하다. 토스는 인증 후 약 10분 안에 승인해야 하므로 24시간 뒤의 승인은 없다고 가정하고, 실제 PG 보장 범위는 샌드박스·문서로 확인한다. 가정 밖의 누락은 전체 대사와 정산 내역 비교가 마지막으로 찾는다.
- 결제를 DONE으로 되살리지 않는 이유: 예매는 이미 FAILED를 받고 HOLD로 돌아갔거나 만료됐다. 결제를 DONE으로 바꾸면 예매와 결제가 어긋난다. 돈을 돌려주는 쪽이 모두에게 일관된다.
- 대가: refund가 FAILED 결제를 가리킬 수 있게 된다. 정산은 "결제 DONE·CANCELED와 refund"뿐 아니라 "FAILED + AUTO_VOID refund"도 0원으로 맞는지 확인해야 한다.

## D13. 환불은 payment가 끝까지 책임진다

- 결정: 예매는 환불을 요청하면 결과를 기다리지 않고 예매를 취소한다(#9의 B안). payment는 일시 장애면 REQUESTED로 두고 복구가 다시 보내며, 업무 거절만 FAILED + 차단 + 경보로 남긴다.
- 이유: 예매가 환불 결과를 기다리면 PG 장애가 예매 취소까지 막는다. 하지만 예매가 다시 요청하지 않으니 payment가 스스로 끝내지 않으면 돈을 돌려주지 못한 채 잊힌다. 일시 장애(연결 실패, 429)를 FAILED로 끝내면 회차 취소 같은 대량 환불에서 대량으로 묻힌다.
- 이 결정만으로는 "환불은 끝났는데 예매 DB 갱신 실패로 예매가 CONFIRMED에 남는" 경우를 막지 못한다. 그래서 예매는 환불 요청 전에 `CANCELING`(티켓 사용 불가)을 커밋하고, 예매 스케줄러가 오래된 `CANCELING`을 다시 요청한다(팀 결정, plan.md 9절 2).
- 결제가 아직 확정 전이면(IN_PROGRESS) 환불을 WAITING으로 받아 두고, 결제가 확정되는 트랜잭션에서 이어 처리한다. 그렇지 않으면 "환불 요청 → 예매 취소 → 그 뒤 결제 DONE"으로 돈만 빠진다. 환불 요청도 payment 행을 먼저 잠그고 상태를 다시 읽어야, 결제 확정과 환불 접수가 엇갈려 WAITING이 DONE 결제 위에 남는 일이 없다.
