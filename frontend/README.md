# 프런트엔드

공연 티켓 예매 화면이다. 회원(예매·쿠폰), 판매자(공연 등록·정산), 관리자(공연장·판매 중지·쿠폰·환불·지급 운영) 화면이 있다. React, TypeScript, Vite, TanStack Query를 쓴다.

```bash
npm install
npm run dev
```

http://localhost:5173 에서 열린다. `/api`는 Gateway(8080), `/fake-pg`는 Fake PG(8090)로 중계한다. 주소가 다르면 `VITE_GATEWAY_URL`, `VITE_FAKE_PG_URL`로 바꾼다.

## 역할

- 로그인 응답에 역할이 없어 `GET /api/users/me`로 읽는다. 메뉴와 화면 진입은 역할을 따르지만 길 안내일 뿐이고, 권한 검사는 서버가 한다.
- 예매·쿠폰함·내 예매는 일반 회원(USER)만 쓴다. 판매자는 `/seller/signup`에서 가입한다.
- MASTER 계정은 가입 API가 없다. 루트 README의 초기 계정을 쓴다.
- 개발 서버(`npm run dev`)의 로그인 화면에는 회원·판매자·관리자 버튼이 있어 누르면 그 계정으로 바로 로그인한다. 계정은 `script/seed-accounts.sh`와 같이 루트 `.env`(없으면 `.env.example`)의 `SEED_USER_*`·`SEED_SELLER_*`·`MASTER_*`를 쓰고, 값을 바꿨으면 개발 서버를 다시 띄운다. 비밀번호가 번들에 들어가므로 빌드본에는 넣지 않는다.

## 대기열

- 회차 `schedule:{scheduleId}`로 room을 조회한다. 해당 room이 없으면 좌석으로 이동하고, 조회 장애는 통과시키지 않는다.
- 오픈 전에는 남은 시간을 표시하고, 오픈 뒤 room entries에 진입한다. 대기 순번은 3초마다 조회하며 차례가 되면 좌석으로 이동한다. 대기 취소도 같은 room에서 처리한다.
- 입장 토큰은 room의 회차 scopes와 함께 탭 저장소(sessionStorage)에 보관한다. 해당 scope가 포함되고 유효 기간이 남은 회차에만 `X-Queue-Token`으로 보낸다. 구형 공연별 토큰은 재사용하지 않고, 로그아웃하면 모두 지운다.
- `QUEUE_TOKEN_INVALID`는 해당 room 토큰을 지우고 대기열을 다시 확인한다. room 없음과 Gateway 거절이 반복되면 자동 왕복을 멈추고 수동 확인을 안내한다.

## 좌석 선택

- layout과 status를 조합해 구역·열·좌석을 표시한다. 상태 비트맵은 서버 layout 순서의 낮은 비트부터 읽으며, 구성 버전이 다르면 layout을 다시 확인한다. 버전·좌석 수가 맞지 않는 응답을 합치지 않는다.
- layout은 ETag/304를 지원하고, status는 3초 간격으로 갱신한다. 선택 표시가 실제 선점 성공을 뜻하지는 않는다.
- 현재 계약은 회원·회차당 1장이다. 선점 성공 후 결제 화면으로 이동한다. 응답 유실·서버 장애로 결과가 불명확하면 같은 좌석 재요청으로 기존 선점 여부를 확인한다.

## 현재 API의 제약

- 홈의 티켓 오픈 캘린더는 메인에 소개된 공연 5개의 회차 응답에서 `bookingOpenAt`을 모아 보여 준다. 전체 공연의 오픈 일정을 조회하는 API는 아니다. 공연 상세의 관람일 달력(`startAt` 기준)과 구분한다.

- 예약 응답에 좌석 이름이 없다. 선택한 브라우저에서는 좌석 선택 때 저장한 이름을 보여 주고, 다른 기기에서는 좌석 수만 보여 준다.
- 결제창은 Fake PG 호출로 대신한다. 운영 PG 연동은 별도 작업이다.
- 판매자 공연·공연장 목록과 단건 조회 API가 없다. 이 브라우저에서 만든 공연·공연장의 version·등급·회차를 localStorage에 기억해 이어서 작업하고, 다른 곳에서 만든 것은 ID와 version을 직접 입력한다. 판매자는 공연장 ID·등급 ID를 관리자에게 받는다.
- 관리자는 회차 version을 읽을 API가 없어 판매 중지에 version을 직접 입력한다. 이 화면에서 바꾼 회차는 응답의 version을 기억해 채운다.
- 내 정보에서 이름·휴대폰 번호를 수정한다. 바뀐 필드만 PATCH로 보내고 저장 응답으로 회원 정보를 갱신한다. 탈퇴는 미구현이다.

## 주문·결제와 쿠폰

- 정액·정률, 최대 할인액·최소 티켓 금액, 적용 장르를 표시한다. 정률은 원 미만을 버리고 할인 후 최소 결제액 100원을 남긴다. 화면 계산은 예상치이며 PG에는 checkout이 반환한 금액을 보낸다.
- 서버 금액이 예상과 다르면 금액을 먼저 갱신하고 다음 클릭에서 진행한다. 승인 결과가 불명확하면 기존 주문·인증값을 유지하고 예약 상태를 확인한다. 이미 결제 중이면 새 준비·승인을 만들지 않는다.
- 이미 해당 예약에 잡힌 쿠폰은 다시 결제할 때 유지한다. 쿠폰 선택을 바꾸면 다음 checkout에서 바뀐 쿠폰을 보내고, 사용 안 함이면 쿠폰 필드를 생략한다. 현재 예약에 잡힌 쿠폰은 유효기간이 지나도 유지될 수 있다.
- 쿠폰함의 일반·웰컴 발급 목록은 서버 category로 나눈다. 보유 쿠폰은 상태별 조회·추가 페이지를 지원하며, category가 없는 회원 쿠폰 응답을 이름으로 분류하지 않는다.
- 현재 예약 응답에는 장르가 없다. 공개 공연 장르로 사용 조건을 안내하지만 실제 예약 장르와 할인 적용은 서버가 최종 검증한다. 관리자는 일반/웰컴 쿠폰의 정액·정률 정책, 기간·수량·장르를 등록·수정하고 신규 발급을 중단할 수 있다. 발급 시작 후 수정 제한과 발급 이력에 따른 삭제 제한을 표시하며 서버가 최종 검증한다.

## 디자인

기본 테마는 다크이며 헤더에서 라이트 모드로 바꿀 수 있다. 선택은 `safe-ticket-theme`에 저장한다. 공통 색상은 `src/styles.css`의 CSS 변수로 관리하고, 확정 로고는 `public/brand/`의 다크·라이트 SVG를 사용한다.

홈의 검색·장르·페이지 조건은 URL에 유지한다. 공연 목록은 5개씩 탐색하고, 작품 배너와 오픈 일정은 검색 필터와 별도로 메인 소개 공연을 표시한다. API 실패·빈 결과를 예시 공연으로 대체하지 않는다.

공연 상세의 관람일 달력은 전체 회차 응답을 받아 서울 날짜 기준으로 월·일별로 표시한다. 월 이동에는 추가 API 요청을 하지 않는다. 최초에는 가장 빠른 예매 가능 회차를 선택하고, 판매 중 회차가 없으면 가까운 미래 날짜만 표시하며, 미래 회차도 없으면 이번 달을 보여 준다. 판매 상태는 오픈·마감 경계, 최대 1분 간격과 창 포커스 복귀 때 갱신한다.

## 내 예매와 예매 상세

- 상태 필터와 페이지 조건을 URL에 유지한다. 기본 목록에서 제외되는 만료·선점 해제 내역은 해당 상태 필터로 조회한다.
- 목록 응답에 없는 포스터·공연장은 화면에 가까운 카드의 예매 상세와 공연 상세로 보완한다. 부가 조회 실패가 예매 상세 진입을 막지는 않는다.
- 결제 대기는 선점 만료 전까지 결제를 이어갈 수 있다. 결제 확인 중·취소 처리 중에는 상태 조회 API를 사용하며 서버의 Retry-After 간격을 따른다.
- 티켓 코드는 확정 상태에서만 표시하고 복사를 지원한다. 취소는 공연 시작 전 확정 예매에만 제공하며 요청 직전 최신 상태를 다시 확인한다.
- 예매 취소와 PG 환불 완료는 구분한다. 만료·선점 해제 후 좌석 재선택은 회차 대기열 확인부터 다시 진행한다.

## 판매자 공연·회차 관리

- 공연 목록은 브라우저 저장 기록만 검색·필터하고 10개씩 표시한다. 서버 전체 목록을 조회한 결과가 아니다.
- 공연 ID·회차 ID로 직접 여는 경로와 수동 version 입력을 제공한다. 모르는 공연 version을 0으로 추정하지 않는다.
- 공연은 초안 등록 → 등급별 가격 → 회차 등록 → 공개 순으로 설정한다. 공개 이후에도 회차를 추가할 수 있지만 가격은 바꿀 수 없다.
- 회차 준비 상태는 판매자 회차 API로 조회한다. PENDING은 자동 조회하며 FAILED는 수동 상태 재확인을 제공한다. 좌석 준비 재요청은 하지 않는다.
- 회차 상세에서 ETag·version을 포함한 관리자 전달 정보를 복사할 수 있다. 좌석 배치는 공개된 공연에서만 조회한다.

## 판매자 정산

- 판매자 메뉴는 공연 관리·회차 관리·정산 내역·지급 계좌로 나눈다. 정산 내역 안에서 정산서·예상 정산 탭을 제공한다. 정산서 발행일·상태·페이지와 예상 정산의 기간·회차·페이지 조건은 URL에 유지한다.
- 예상 정산은 서울 기준 금융 발생일의 판매자 몫 순변동이다. 지급 가능액·현금·미지급액으로 표시하지 않는다. 최대 31일을 조회하고 집계 준비 중(null)·갱신 지연·정상 0원을 구분한다.
- 미회수 차감은 다음 정산에서 아직 상계하지 못한 잔액으로 별도 표시한다. 지급액과 합산하지 않는다.
- 계좌 최초 등록은 조회 결과가 등록 전일 때만 If-Match 없이 요청한다. 수정은 입력 시작 시점의 ETag/version을 사용한다. 충돌 시 재조회한 정보를 사용자가 확인한 후 다시 저장한다.
- 계좌번호·예금주 원문은 브라우저 저장소나 로그에 남기지 않는다. 화면과 서버 응답은 마스킹 값을 사용하며, 입력은 저장 성공·취소 시 지운다.

## 관리자 공연장·좌석·회차·대기열

- 공연장 관리에는 브라우저 기록 목록과 기본 정보/등급·좌석 탭을 제공한다. 새 공연장 → 등급 → 물리 좌석 순으로 등록한다. 기록만 지우는 기능과 ID 직접 열기도 유지한다.
- 물리 좌석은 숫자 범위(10-12), 영문 범위(A-C), 직접 열 목록(가,나)을 지원한다. 전체 배열을 만들기 전에 1~5,000석과 열·등급을 검증한다. 미리보기는 처음 3열·열당 12석까지만 표시한다.
- 공연장과 회차의 version은 서로 다르다. 확인하지 못한 version을 0으로 추정하지 않는다. 회차 운영은 공개 조회와 판매자에게 받은 version으로 판매 중지·재개를 처리한다. 중지는 신규 선점만 막는다.
- 대기열 관리에서 회차 ID 묶음을 schedule scope로 생성하고 scope로 조회한다. 1~100개, 오픈 최소 1분 이후, 종료는 오픈 이후 조건을 적용한다. 수정·삭제·조기 종료·입장량 설정 기능은 API에 없어 제공하지 않는다.
- 대기열 목록은 브라우저에 기록한 room 스냅샷이다. 실제 연결은 scope 조회로 확인하며, 조회 404와 서비스 장애를 구분한다.

## 관리자 환불·지급 운영

- 환불 목록은 미완료 건의 상태·복구 모드·PG·경과 시간으로 조회하고 커서로 더 불러온다.
- 환불 상세의 PG 조회는 버튼을 눌렀을 때만 읽기 전용으로 수행한다.
- 재시도·조회 전용 재개는 확인창을 거쳐 서버가 상태·버전·시도·사유를 검증한다.
- 지급 운영은 판매자 지급 / 미회수 차감 탭으로 나눈다. 지급 상태와 확인 항목 필터를 URL로 유지한다.
- 결과 불명·조회 전용·완료된 지급은 재시도하지 않는다. 확정 실패만 메모와 기대 버전·시도를 보내 대기로 되돌린다.
- 응답 불명 후에는 동일 commandId·경로·사유/메모·기대 상태 전체를 유지한다.
  요청 결과를 확인하기 전까지 이 화면을 유지해야 한다. 새로고침·탭 종료를 넘는 명령 보존은 제공하지 않는다.
- 명령 접수와 실제 환불·송금 완료는 구분해 표시한다. 목록의 불러온 건수는 전체 집계가 아니다.
- 자동 검증: `node --test tests/*.test.mjs`. 운영 명령 재전송·기간 필터를 포함한다.
