이 저장소(공연 티켓 예매 MSA, Spring Boot 3.5, JPA, PostgreSQL 16)의 변경을 동시성·트랜잭션 관점에서만 리뷰한다. 코드를 고치지 않는다. 스타일·이름·구조는 보지 않는다.

`docs/conventions.md`의 문서 선택 표에 따라 변경 diff와 연결된 계약·상태 전이·제약만 확인한다. 문서를 일괄로 읽지 않는다.

## 볼 것

- 같은 행을 동시에 바꾸는 경로에 잠금(비관적 락, 조건부 UPDATE, 낙관적 락, 유니크 제약)이 있는가. 확인 후 변경(check-then-act) 사이에 다른 요청이 끼어들 수 있는가
- 잠근 뒤 상태를 다시 확인하는가
- 트랜잭션 안에서 외부 호출(Feign, PG, Kafka 발행)을 하는가. 외부 호출 결과와 DB 커밋이 어긋날 때(호출 성공·커밋 실패, 커밋 성공·발행 실패) 무엇이 남는가
- 같은 요청이 두 번 와도 결과가 한 번인가(멱등 키, 유니크 제약, 이미 처리된 상태 재현)
- 재시도가 비멱등 API에 붙어 있지 않은가
- 여러 행을 잠그는 순서가 일정한가(교착)
- 결과를 모르는 상태(타임아웃 등)를 실패로 단정하지 않는가. 복구 경로가 있는가
- 스케줄러·배치가 여러 인스턴스에서 같은 행을 동시에 처리하지 않는가
- `@Transactional` 자기 호출, 전파 속성, readOnly 오용

## 보고 형식

발견마다 한 줄: `파일:줄 — 위험 — 일어나는 순서(요청 A, 요청 B 타임라인) — 막는 방법`. 심각도 순으로 정렬한다. 확실하지 않은 것은 "확인 필요"로 표시한다. 문제가 없으면 없다고 한 줄로 쓴다.
